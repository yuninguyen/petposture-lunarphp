# PetPosture — Architecture

Headless e-commerce: **Next.js 16 (App Router)** storefront + **Laravel 11 / Lunar PHP** commerce API, both deployed as separate Docker containers on a single VPS behind Cloudflare. No Vercel, no separate CI service — a `build.js` script run on `git push` is the entire deploy pipeline.

## Frontend — `frontend/`

- **Next.js 16.2.3, React 19.2.4**, App Router only (`app/`), TypeScript strict mode.
- **No state library, no axios/swr/react-query.** Every API call is a plain `fetch()` against `getApiBaseUrl()` (`frontend/lib/api.ts`), which resolves the backend origin from `NEXT_PUBLIC_API_URL` (prod) or `127.0.0.1:8000` (local dev).
- Pages live in `app/<route>/page.tsx` and are thin — they just import and render a matching component from `components/` (e.g. `app/returns/page.tsx` → `components/RequestReturnPage.tsx`). All real UI logic lives in `components/`.
- `components/` is flat for top-level pages (`ShopPage.tsx`, `RequestReturnPage.tsx`, `ReturnRefundPolicyPage.tsx`, …) with subfolders for cross-cutting concerns: `components/auth/`, `components/checkout/`, `components/orders/`, `components/product/`, `components/shop/`.
- Auth: Sanctum bearer token issued by the backend, stored client-side via `context/AuthContext`, also mirrored into an httpOnly `petposture_token` cookie by the backend on login.
- Pages that read `useSearchParams()` (e.g. `checkout/success`, `returns`) always wrap the content in `<Suspense>` at the default-export level — required by the App Router, not optional.
- Styling: Tailwind v4, no CSS-in-JS. Animation: `framer-motion`. Icons: `lucide-react`.
- Production runs a custom `server.js` (not `next start`) inside `Dockerfile.prod` — single-stage Node 20 Alpine image, `npm run build` at image build time.
- **`frontend/AGENTS.md` is load-bearing, not boilerplate**: this Next.js/React version is newer than most training data — read `node_modules/next/dist/docs/` before writing anything non-trivial.
- **Accessible-orange design tokens (`ink`, `rust`, added 2026-08-13)**: a real production Lighthouse audit found sitewide WCAG AA contrast failures against the brand orange (`secondary`, `#df8448`) — white text on orange backgrounds (2.78:1, needs 4.5:1) and orange used as text on white/light backgrounds (also below 4.5:1, needs ~6.6:1 as text). Rather than change the orange itself, two new single-purpose tokens were added, synced across all three token sources per the established triplication convention (`tailwind.config.ts`'s `colors`, `lib/uiTheme.ts`'s `C` inline-style object, `app/tokens.css`'s CSS custom properties — though `ink` was only added to the first two, not `tokens.css`, since nothing consumes it as a raw CSS variable): `ink` (`#1a2128`, near-black, 5.63:1 against the orange) for text/icons sitting **on top of** an orange background; `rust` (`#8f4a1f`, 6.63:1 against white) for orange-as-text **on** white/light backgrounds (eyebrow labels, prices). **These two, plus the pre-existing `secondary.dark`/`secondaryHover` (`#c9713a`, hover-*background* only), must stay single-purpose** — an initial version of this fix reused `secondary.dark` for the text-on-white case too, which shipped a real regression (orange button hover backgrounds went noticeably too dark, caught by the user from a live screenshot) before being split apart. See `RULES.md` for the "one token, one purpose" rule this became.
- **Domain canonicalization (added 2026-08-10)**: `petposture.com` (non-www) is canonical. `lib/site.ts`'s `SITE_URL` feeds `app/robots.ts` (sitemap URL) and `app/sitemap.ts` (every URL), and every one of the 21 public routes sets its own `alternates: { canonical: '/path' }` (no site-wide default — `metadataBase` on its own does not emit a canonical tag). `www.petposture.com` 301s to non-www via a Cloudflare Redirect Rule (zone `7c77d5e7f534eb3da62f474ec3c88e0a`, `http_request_dynamic_redirect` phase), created via the Cloudflare API rather than the dashboard. Fixed after discovering both domains served identical 200 content with neither a redirect nor a canonical tag between them — a duplicate-content risk found incidentally while investigating an unrelated (and ultimately unfounded) Googlebot 4xx/5xx report. See `RULES.md` for the rule this became for any new route.

## Backend — `backend/`

- **Laravel 11**, PHP 8.3, no `Kernel.php` (`bootstrap/app.php`-based config). **Lunar PHP 1.x** is the commerce core (`Order`, `OrderLine`, `Customer`, `Product` models come from `Lunar\Models\*`, not app-owned models).
- **App-owned commerce logic sits in `app/Services/*.php`**, one class per concern (`OrderOperationsService`, `ReturnRequestService`, `CheckoutService`, `StripePaymentIntentService`, `AfterShipService`, `ShippingService`, `SalesTaxService`, …). Controllers stay thin: validate → call a service → return a `JsonResource`.
- Order lifecycle state machine lives in `app/Support/Orders/OrderStateMachine.php` — the single source of truth for allowed status transitions (`awaiting-payment → payment-offline/payment-received/cancelled → processing → shipped → delivered`). Never hand-roll a status transition; go through `OrderOperationsService::update()`/`performAction()`, which calls the state machine and fires the matching customer email + webhook.
- **Three separate status concepts on an order — do not conflate them:**
  1. `status` (the state machine column above) — the admin panel labels this **"Order Status"**.
  2. `meta.payment_status` (`awaiting-payment` / `pending` / `paid` / `partially-refunded` / `refunded` / `failed` / `cancelled`, set by `OrderOperationsService::refundOrder()` and `OrderStateMachine::applyDerivedStatuses()`) — labeled **"Payment Status"** in the admin panel. `status` never becomes `"refunded"`; a `delivered` order that gets refunded is still `delivered` (it happened), not retroactively un-delivered — conflating the two into one badge would lose that.
  3. `meta.fulfillment_status` (`unfulfilled` / `processing` / `shipped` / `delivered` / `cancelled` / `returned`, derived by `OrderStateMachine::applyDerivedStatuses()`/`resolveFulfillmentStatus()`) — a **different value set from `status`** (it has `returned`/`unfulfilled`, `status` never does), exposed to customers via `Api\OrderResource` (`/account`, `/checkout/success`). **Do not label anything "Fulfillment Status" in the admin panel** — that name is already this field's, and it means something else there; the admin `status` badge is "Order Status".
  The admin Order view (`ViewOrder.php`) shows "Order Status" and "Payment Status" as two separate color-coded badges side by side in the Order Summary section (plus Payment Method and Refund Reason as plain fields next to them) specifically so a partial refund doesn't read as if the whole order silently changed state.
- Order metadata (payment/refund/shipment/fulfillment state, timestamps) is stored in the `lunar_orders.meta` JSON column, not new columns — this is the established extension point for anything scalar/mutable on an order. New **relational, multi-row, audited** concepts (e.g. `order_events`, `order_return_requests` + `order_return_request_items`) get their own migration/table instead.
- **Admin panel = Filament 3**, auto-discovered from `app/Filament/Resources/*.php` (no manual registration for app-owned resources). Resources are grouped via `getNavigationGroup()`; commerce resources (Orders, Return Requests, Shipping Costs, Discounts, Customer Groups, Customers, Customer Review) all still return `__('lunarpanel::global.sections.sales')` — that translation key's **displayed label** was renamed to "🛒 Commerce" (`lang/vendor/lunarpanel/en|vi/global.php`), but the key itself didn't change. Use the same `sales` key for a new commerce resource, not a literal `__('Commerce')` string — that would silently create a second, empty-looking duplicate group.
- **Overriding a Lunar vendor resource (Product, Customer, Role, CollectionGroup today) requires a local class, not just config.** Pattern: `app/Filament/Resources/XResource.php extends Lunar\Admin\Filament\Resources\XResource` (or Shield's `RoleResource` for Role), override `getDefaultTable()`/`getTableColumns()`/`getDefaultPages()` as needed, then remove the vendor class from `AdminPanelProvider`'s explicit `->resources([...])` array so only the local one registers (`discoverResources` picks it up automatically — don't list both, that double-registers the same slug). **Gotcha**: Lunar's own sub-pages (**list/edit/view/etc., not just edit/view**) hardcode `protected static string $resource = VendorResource::class` — if a page's breadcrumbs/URLs, or a **table override specifically**, need to take effect, you must also create a local page subclass (`extends Lunar\...\Pages\ListX as BaseListX`) that only overrides `$resource`, and wire it via the local resource's `getDefaultPages()`. Pages you don't touch (still pointing at the vendor class) keep working anyway, since Filament resolves URLs by route *name* (derived from slug), not by which resource class is currently registered — confirmed working for `ProductResource`'s untouched edit/pricing/inventory/etc. pages after only overriding `index`. **This bit twice**: `CustomerResource`'s `getDefaultTable()` override (added 2026-08-07, new Name/Email/Total Orders/Total Spent/Joined/Status columns) silently never rendered — `/admin/customers` kept showing Lunar's stock columns — because `ListCustomers` (the `index` page) was still Lunar's own class, which resolves `table()` against *its own* `$resource` (Lunar's base `CustomerResource`), not the locally-registered one. `ViewCustomer` had already been fixed this way for a different reason (relation-manager routing); `ListCustomers` needed the identical fix before the table override actually took effect. If a `getDefaultTable()`/`getDefaultForm()` override on a resource doesn't visibly apply, check whether *that specific page* (`list`/`edit`/`view`) has a local subclass yet before assuming the override itself is wrong.
- **Relation manager panels on a resource's View page lazy-load via `x-intersect` (IntersectionObserver), not on page load.** The panel HTML only fetches once it actually scrolls into the browser's real viewport — a headless-browser screenshot/scrape taken right after page load (before scrolling) will see a permanent `animate-pulse` skeleton and nothing else, even though there's no error (confirmed via network/log tracing while debugging the Customer Address Book table this session — cost real time before the cause was found). When verifying a relation manager's content programmatically (Playwright, etc.), use a tall viewport or scroll the panel into view and wait, don't just wait longer at the same scroll position.
- **Header Edit/Delete action styling is set globally, once**, not per-page: `AdminPanelProvider::panel()` calls `Filament\Actions\EditAction::configureUsing(...)` / `DeleteAction::configureUsing(...)` (outlined, brand-orange for Edit, red for Delete) — this is Filament's built-in `Configurable` trait (`Component::configureUsing()`), and it applies panel-wide to every `Filament\Actions\EditAction`/`DeleteAction` instance, local resources and untouched Lunar vendor pages alike, without editing each page. Don't hand-style an individual page's header actions to "fix" its color — fix (or add to) the global `configureUsing()` call instead, or the next vendor resource you haven't touched yet will still show the unstyled default. This is scoped to `Filament\Actions\*` (page header actions) only — `Filament\Tables\Actions\*` (compact row/kebab-menu icon actions) is a separate class hierarchy and intentionally left at Filament's default, denser styling.
- **Products table** (`app/Filament/Resources/ProductResource.php`) has row-level quick-edit for Stock and Status: clicking the value opens a small modal (`Tables\Actions\Action` bound via `TextColumn::action()`, not a full edit page). Stock's quick-edit is **only shown when the product has exactly one variant** (`$record->variants->count() === 1`) — the column itself displays `variants_sum_stock` (a sum across variants), so editing that single number is only unambiguous for a single-variant product; multi-variant products just show the sum, no pencil.
- **API auth**: Laravel Sanctum, backed by the app's own `User` model (not `Lunar\Models\Customer` directly) — `CustomerLinkService` links a `User` to a Lunar `Customer` on registration. Guest flows (checkout, order tracking, return requests) resolve by `(order reference OR meta->tracking_number) + customer_reference email`, no auth required, always throttled.
- **Transactional email**: custom Blade views under `resources/views/mail/*.blade.php` (not Laravel's markdown mail for anything customer-facing today — those were migrated off markdown to full custom HTML for design control). Every mail view needs the font-family inline on *every* element (no CSS inliner runs for `Content(view: …)` mailables) and the logo via `$message->embed()` for real `Content-ID` embedding — Gmail strips `data:` URIs and hosted-URL images get blocked by BIC in some clients.
- **Mobile-responsive email CSS (added 2026-07-30)**: 11 of the 19 templates use a fixed-width 2-column or fixed-padding layout that didn't collapse on narrow clients — none of the 19 had a single `@media` query before this. Added a shared `@media (max-width:600px)` block per file (`.stack-col`/`.stack-gap`/`.full-col`/`.mail-px` classes) inside each template's `<style>`, applied *alongside* the existing inline styles as progressive enhancement — never remove or replace an inline style, since that's still what non-`@media`-aware clients (older Outlook) render. The other 8 templates (`order-delivered`, `order-shipped`, `order-returned`, and the 5 return-status emails) have no 2-column/fixed-width pattern and were left untouched.
- **Payments**: Stripe, custom integration (no `laravel/cashier`) via `StripePaymentIntentService` + `Payments/Gateways/StripeCardGateway.php`. Stripe keys/webhook secret are DB `Setting` values (5-min cache), falling back to `.env` — always read both places the same way `StripePaymentIntentService` does, or checkout breaks silently. **PayPal** (added 2026-07-26) follows the identical shape: `PayPalService` (OAuth client-credentials, Orders API v2 create/capture, refunds via `/v2/payments/captures/{id}/refund`, webhook signature verification) + `Payments/Gateways/PayPalGateway.php`, same DB-`Setting`-overrides-`.env` credential pattern, same 5-min cache. `OrderOperationsService::refundOrder()` and the auto-refund-on-cancel path in `update()` both branch on `meta.payment_gateway` (`stripe` vs `paypal`) rather than assuming Stripe — if you add a third gateway, every place that currently branches `stripe`/`paypal` needs the new case too, not just the payment/refund calls. Frontend renders PayPal's own Smart Buttons inline in checkout (popup approval flow via `createOrder`/`onApprove`, matching how Shopify implements PayPal) rather than a full-page redirect — see `frontend/app/checkout/page.tsx`.
- **Redirect-checkout gateways — Airwallex, Payoneer, PingPong (added 2026-08-07)**: a new `collection: 'redirect'` type alongside `direct` (Stripe) and `popup` (PayPal) — the shopper's browser is bounced to the gateway's own hosted payment page and back, rather than an embedded field or JS popup. Session creation happens **before** `placeOrder()` (mirroring how PayPal's order is created first): `POST /api/checkout/{gateway}-session` generates a correlation token server-side, bakes it into the gateway's `return_url` (`/checkout/success?gateway=&session_id=`) *before* calling the vendor API — this ordering matters, since the vendor's own session id isn't known until after the call, but the return URL has to be handed to the vendor at creation time. `placeOrder()` then stores that same token as `meta.{gateway}_session_id` on the order. When the shopper is bounced back, the checkout success page can't use the normal reference+email lookup (the Lunar order reference didn't exist yet when the gateway redirect was set up) — it resolves the order instead via the new public `GET /api/orders/by-payment-session?gateway=&session_id=`. Unlike Stripe (own `StripeWebhookEvent` table) and PayPal (own `PayPalWebhookEvent` table), these three share **one** `payment_webhook_events` table (`gateway`+`event_id` unique) and **one** `OrderOperationsService::syncRedirectGatewayPayment()` sync method — they don't need Stripe's extra fraud/card-brand fields, so three near-duplicate tables/methods would have been pure duplication. **Confidence caveat**: PingPong's `prePay` request/response shape is doc-verified; Airwallex's Payment Links endpoint and Payoneer's Checkout session endpoint are best-effort reconstructions (their docs sites didn't yield a scrapeable API reference) and need confirming against a real sandbox account before either is switched to live mode.
- **AI SEO generation (`AiSeoGeneratorService`, added 2026-08-07)**: the Post SEO Settings section's "Generate with AI" button calls Claude Opus 5 via the official `anthropic-ai/sdk` PHP package (structured `outputConfig.format` → `json_schema`, so the response is parsed directly, no regex/markdown scraping) to draft SEO title, focus keyphrase, meta description, and social title/description from the post's own title+content. **Fourth instance of the DB-`Setting`-overrides-`.env` credential pattern** (Stripe/PayPal/redirect-gateways precedent): `Setting::get('anthropic_api_key') ?: config('services.anthropic.key')`, cached 5 minutes. Unconfigured → `isConfigured()` returns false and the button throws a clear `RuntimeException` instead of a silent/confusing API error. **Update 2026-08-13**: `ANTHROPIC_API_KEY` is now set on the production VPS's `backend/.env` (container recreated to pick it up — `env_file:` values only load at container start, not live). Verified the key itself authenticates correctly by calling `AiSeoGeneratorService::generate()` directly, but the Anthropic account has **no credit balance** — every request currently fails with `"Your credit balance is too low to access the Anthropic API"`. The button will keep erroring (now with a billing error, not a missing-key error) until the Anthropic Console account is topped up.
- **Shipment tracking (multi-shipment, added 2026-07-25)**: an order can have multiple shipments (`order_shipments` + `order_shipment_items`, mirroring the `order_return_requests` shape below), each covering a subset of order lines with its own tracking number/carrier — not every item has to ship in one package. `OrderOperationsService::recordShipment()` is the single write path (validates items belong to the order and don't exceed remaining shippable quantity per line); a real tracking number is **required**, there is no silent placeholder fallback anymore. The AfterShip webhook (`/api/webhooks/aftership`, HMAC-verified, no auth middleware) matches the incoming event to a specific `order_shipments` row by tracking number and only auto-marks the **order** delivered once **every** shipment on it reports delivered. The "Order Shipped" customer email fires once per shipment (not once per order), showing only that shipment's items/tracking. Legacy `meta.tracking_number`/`meta.shipments[]` fields are still kept in sync for backward compatibility (the admin API route used by the Next.js `/admin/orders/[id]` page reads shipment history from there, not from the new tables) but are no longer the source of truth for anything new.
- **Scheduler (added 2026-07-25)**: `php artisan schedule:work` runs as its own supervisord process (`returns:expire-overdue` today is the only scheduled command — see `routes/console.php`). There's no OS-level cron in the container, so a `Schedule::command()` registration does nothing unless this process is running — always add both when introducing a new scheduled task.
- **Edge caching**: Cloudflare Cache Rule on the `petposture.com` zone caches `GET` requests to the non-personalized catalog/content endpoints (`/api/products*`, `/api/brands*`, `/api/posts*`, `/api/settings`, `/api/categories`, `/api/blog/categories`, `/api/checkout/payment-methods`) for 5 minutes at the edge, `override_origin` (Laravel sends `Cache-Control: private` by default, so the rule must explicitly override it). `App\Services\CloudflareCacheService::purgeAll()` is called by 4 model observers (`ProductCacheObserver`, `BrandCacheObserver`, `PostCacheObserver`, `SettingCacheObserver`) whenever the underlying record is saved/deleted — it does a full-zone `purge_everything`, not a targeted per-URL purge, because purging by specific URL (`files` array) was verified in production to silently no-op for entries cached via `override_origin` when the origin sent `Cache-Control: private`. **Never add a personalized/authenticated endpoint to this Cache Rule** — cart, checkout, orders, admin, and webhooks must never be cached this way. Credentials (`CLOUDFLARE_API_TOKEN`/`CLOUDFLARE_ZONE_ID`) live only in the VPS's `backend/.env`, never in git. **Root-caused and fixed 2026-08-13** (found 2026-07-26): `/checkout` and `/checkout/success` were being served stale from the Cloudflare edge after frontend deploys. The documented Cache Rule above only targets `/api/*` GET paths and was never the cause — the real culprit was a **separate, zone-wide "Cache HTML pages" Cache Settings rule** (`expression: not starts_with(http.request.uri.path, "/api/")`, `edge_ttl: bypass_by_default` — i.e. it caches any non-`/api/` path *if the origin sends a cacheable `Cache-Control` header*). Both checkout pages had no `export const dynamic = 'force-dynamic'`, so Next.js statically prerendered them and served `Cache-Control: s-maxage=3600, stale-while-revalidate=...` — confirmed directly via `curl -I http://127.0.0.1:3001/checkout` on the VPS (`x-nextjs-prerender: 1`, that exact header). Cloudflare then dutifully cached that stale shell for up to an hour after every deploy. Fixed by restructuring both routes: `app/checkout/page.tsx` and `app/checkout/success/page.tsx` are now thin server wrappers exporting `dynamic = 'force-dynamic'` (this segment config can't coexist with `"use client"`, which both pages had at the top level), rendering the original client code moved unchanged into `frontend/components/CheckoutPage.tsx`/`CheckoutSuccessPage.tsx`. Verified via a production build: both routes flipped from prerendered to `ƒ (Dynamic)` in the route-type table. **General lesson, extends the Pages-CMS lesson below**: any page that must never be edge-cached (checkout, cart, account, or anything reading per-user state) needs `force-dynamic` explicitly — Next.js will silently static-prerender a page with no obvious dynamic data dependency, and Cloudflare's zone-wide HTML cache rule will then cache whatever `Cache-Control` header that static build produces.
- **Return requests (added 2026-07-25)**: separately from the outbound shipment tracking above, `order_return_requests` now also captures the customer's own return-shipment tracking (`return_tracking_number`/`return_carrier`/`package_received_at`, set via a dedicated "Add Return Tracking" admin action) — this is informational only today (a note/badge on the admin table), it does **not** auto-drive the return's status. An approved return request with no tracking number 7 days after approval auto-expires (`ReturnRequestService::expireOverdueRequests()`, run daily by the scheduler) and emails the customer — separate from, and independent of, the original 30-day return-eligibility window (`RETURN_WINDOW_DAYS`), which only gates whether a return request can be *created* in the first place.
- **Shop by Breed / Shop by Solution (added 2026-08-02)**: two orthogonal product facets alongside the existing category filter — `breed_tags` (`flat-faced`/`long-backed`) and `solution_tags` (`eating-digestion`/`mobility-support`/`comfort-safety`), stored as comma-separated Lunar attributes (registered via migration, same pattern as the technical-spec attributes) and exposed on `ProductResource` as `breedTags`/`solutionTags` arrays. `ProductController@index` filters on them via `?breed=` / `?solution=`, matched with a `LIKE` against the JSON `attribute_data` column — **MySQL, not Postgres**, so this must be `CAST(attribute_data AS CHAR)`, not `AS TEXT` (a Postgres-only cast that was silently 500ing this filter, plus the pre-existing `badge`/`q` search filters that used the same wrong cast, until fixed 2026-08-02). Frontend: `frontend/lib/shopData.ts`'s `BREED_CONTENT`/`SOLUTION_CONTENT` are the single source of truth for each variant's title/description/image — both the picker index pages (`/shop/breeds`, `/shop/solutions`) and the specific landing pages (`/shop/breeds/[slug]`, `/shop/solutions/[slug]`) import from there rather than duplicating copy. A product can carry both a breed tag and a solution tag independently (e.g. a harness tagged `flat-faced,long-backed` **and** `comfort-safety`) — don't model this as a nested category hierarchy.
- **Wishlist (added 2026-08-01)**: `user_wishlist_items` (`user_id` + `lunar_product_id`, unique pair) via `WishlistService` + `WishlistController` (`GET/POST/DELETE /api/me/wishlist`, `auth:sanctum` only — no guest endpoint). Deliberately **guest-local-only, no server sync**: logged-out visitors get `localStorage` (`petposture_wishlist`, full `Product` snapshots so the page renders without extra fetches) with zero backend calls, and there is no merge-on-login — this is the same shape as checkout's guest "save address" (`petposture_guest_address`), now a second instance of the pattern. `frontend/context/WishlistContext.tsx` forks entirely on `useAuth().token`: guest reads/writes localStorage via `useSyncExternalStore`, logged-in reads/writes the API and never touches localStorage. Identity uses the Lunar product's own `id` field, not the frontend `Product.productId` field — the latter is never populated by `ProductResource` (a pre-existing, unfixed gap; anything filtering by `.productId` elsewhere in the frontend is comparing `undefined`).
- **Affiliate comparison content + click tracking (`AffiliateNetwork`/comparison posts added 2026-08-05, click tracking added 2026-08-07)**: `Post.type = 'comparison'` (alongside `article`/`guide`) renders retailer price-comparison cards above the article body — `metadata.comparison_items` (Filament repeater on `PostResource`: product name/image, retailer, price, rating, pros/cons, `affiliate_url`, and an `in_stock` toggle added 2026-08-09 that surfaces a "⚠ Out of stock" badge inline on the post title in the admin Posts list, per-item rather than per-post) resolved against the admin-managed `affiliate_networks` table (name/slug/logo/active, `AffiliateNetworkResource` under Content Management) so retailer display name/logo aren't hardcoded anywhere. ## Data flow: adding a customer-facing feature (reference shape)

The "Request a Return" feature (Phase 1) is the current reference implementation for this shape — new features should follow it:

1. Migration + model(s) in `app/Models/` (dedicated table if the data is relational/audited, `meta` JSON if it's scalar order state).
2. A single `App\Services\*Service` class owns all mutation + validation logic (`ValidationException::withMessages()` for business-rule rejections) and fires customer email(s) directly (`Mail::to(...)->send(...)`) — no queued job unless the trigger is a webhook/background event.
3. `App\Http\Resources\Api\*Resource` (`JsonResource`) for the API shape; controller stays a thin validate-then-delegate layer.
4. Routes: public/guest routes at top level of `routes/api.php` (throttled), admin routes inside the existing `Route::prefix('/admin')->middleware(['auth:sanctum', 'role:...'])` group, authenticated-customer routes inside the existing bare `auth:sanctum` group.
5. Filament `Resource` for admin review/action if staff need to work the queue (approve/reject/complete-style actions as `Tables\Actions\Action::make()` with a `->form([...])` modal, not a full edit page).
6. Frontend: a `components/<Name>Page.tsx` + thin `app/<route>/page.tsx`, reusing the existing guest-lookup pattern (`/api/orders/track`-style reference+email lookup) rather than inventing a new one.
7. Deploy: `git push` (runs `build.js`) → SSH to VPS → `git pull && docker compose -f docker-compose.prod.yml build <service> && up -d --force-recreate <service>` → `php artisan migrate --force` runs automatically via the backend container's entrypoint on every start.

## Deployment

- **No CI service.** `build.js` at the repo root runs on `git push` (see `RULES.md` for exact steps) — it installs deps and runs both production builds locally as a push-time smoke test. It does **not** run tests or linters.
- **Production**: single VPS, `docker-compose.prod.yml`, three services (`redis`, `backend`, `frontend`), all `network_mode: host` — no bridge networking, no port-mapping section, ports are just whatever `$PORT` each app binds to.
- Manual deploy after every merge: SSH in, `git pull`, `docker compose build` the changed service(s), `up -d --force-recreate`. Migrations run automatically on backend container start (baked into the Docker entrypoint), but hotpatching a single file via `docker cp` for a quick test does **not** persist — always follow up with the real `git pull` + rebuild, or the next deploy silently reverts the hotpatch.
- GitNexus (`npx gitnexus analyze`) reindexes the code graph — run it after every deploy per root `CLAUDE.md`.
- **Host-level nginx + fail2ban (found 2026-07-27, previously undocumented)**: a system `nginx` (not containerized, not in `docker-compose.prod.yml`) actually terminates :80/:443 on the VPS and `proxy_pass`es to the `frontend`/`backend` containers by `server_name` — Cloudflare proxies to *this*, not directly to the Docker containers. This same nginx also fronts an unrelated second site (`rebateops.online`) on the same VPS. `fail2ban` (`nginx-badbots` jail, `/etc/fail2ban/jail.d/nginx-badbots.conf`) tails `/var/log/nginx/access.log` and permanently `deny`s (via `/etc/nginx/conf.d/fail2ban-autoban.conf`) any IP that matches a known scanner-probe pattern (`.env`, `wp-login.php`, `.git/config`, etc.) — **one match bans the IP from every path on every site on this nginx for 24h** (`bantime`, lowered from the original 7 days 2026-07-27 — see below). A banned IP gets a raw `403 Forbidden` / `nginx` page that never reaches Cloudflare's or Laravel's own error handling, so it's easy to mistake for a site outage or a Cloudflare block when it's actually this layer.
  **Real incident**: a customer (residential Vietnam ISP, likely CGNAT-shared IP) got 403'd site-wide after this same IP happened to run `.env`-probing `curl` commands during an unrelated security audit in this same session — a stray audit request, not malicious customer behavior, triggered a week-long ban that would have collaterally blocked anyone sharing that IP. Unbanned via `fail2ban-client set nginx-badbots unbanip <ip>`; `bantime` dropped from `604800` to `86400` to shrink the blast radius of any future false positive (`maxretry` deliberately left at `1` — the filter patterns are specific enough that legitimate traffic shouldn't match them at all). If this happens again: `fail2ban-client status nginx-badbots` lists currently-banned IPs; `grep '<ip>' /var/log/nginx/access.log` shows what request actually triggered it.

# PetPosture — Rules

Read this before touching code. See `ARCHITECTURE.md` for the why; this file is just the enforceable rules.

## Coding conventions

**PHP (backend)**
- Laravel Pint (`laravel` preset) formats everything — run `composer format` before committing PHP, don't hand-format.
- `larastan`/PHPStan level 3 (`phpstan.neon`) — run `composer analyse`.
- Constructor property promotion + `private readonly` for service dependencies (`public function __construct(private readonly XService $x)`).
- One class per concern in `app/Services/*.php`. Controllers validate + delegate to a service; they do not contain business logic.
- Business-rule rejections throw `ValidationException::withMessages([...])` from the **service**, not the controller — let Laravel's default handler format the 422.
- Never mutate order status by hand (`$order->update(['status' => ...])`). Always go through `OrderOperationsService::update()`/`performAction()` so the state machine, emails, and webhooks stay in sync.
- New scalar/mutable order state → `meta` JSON key. New relational/audited data (multiple rows, own lifecycle) → its own migration + model, matching the `order_events` / `order_return_requests` / `order_shipments` precedent.
- Shipment tracking numbers are **required**, never silently defaulted (no "fall back to the order reference" placeholder) — `OrderOperationsService::update()`/`recordShipment()` both throw `ValidationException` on a blank `tracking_number` rather than inventing one.
- Refund reasons are a fixed select (`OrderOperationsService::REFUND_REASON_LABELS`), not free text — keeps refund-without-return cases reportable/auditable. Add new reasons to that const, don't accept an arbitrary string.
- Adding a `Schedule::command(...)` to `routes/console.php` does nothing by itself — `supervisord.conf` must also run `php artisan schedule:work` (there's no OS cron in the container). Always add/verify both together.
- Comments: sparse, by convention. Only for non-obvious *why* (a workaround, a hidden constraint). Never restate what the code already says.
- Filament resources: auto-discovered, no manual registration for app-owned resources. Commerce resources go in `getNavigationGroup() { return __('lunarpanel::global.sections.sales'); }` (displayed as "🛒 Commerce", the key itself is unchanged) — don't invent a new nav group.
- **Overriding a Lunar/Shield vendor resource** (Product, Customer, Role, CollectionGroup are the precedent): create `app/Filament/Resources/XResource.php extends <vendor XResource>`, override only what you need (`getDefaultTable()`, `getDefaultPages()`, etc.), then remove the vendor class from `AdminPanelProvider`'s explicit `->resources([...])` array so it doesn't double-register alongside the auto-discovered local one. If a specific vendor sub-page's breadcrumbs/relations need to point at the local resource, add a local page subclass that only overrides `$resource` — untouched vendor sub-pages keep working as-is (see `ARCHITECTURE.md`). **This includes the `list` page, not just `edit`/`view`**: a `getDefaultTable()` override silently does nothing if the resource's `index` page is still Lunar's own `ListX` class, since it resolves the table against *its own* hardcoded `$resource`, not the locally-registered override (`CustomerResource`'s new columns didn't render until a local `ListCustomers` page subclass was added — see `ARCHITECTURE.md`). If a table/form override doesn't visibly apply, check the relevant page's `$resource` before assuming the override itself is wrong.
- **Don't hand-style an individual page's Edit/Delete header action.** `AdminPanelProvider::panel()` sets the color/icon/outline for every `Filament\Actions\EditAction`/`DeleteAction` globally via `::configureUsing()` — Edit is outlined+orange, Delete is outlined+red, panel-wide. If a button looks wrong, fix that one global call, don't add a one-off `->color()`/`->outlined()` override to the page.
- Order has three distinct status fields (`status`, `meta.payment_status`, `meta.fulfillment_status` — see `ARCHITECTURE.md`) with overlapping but different value sets. Never label a badge/column ambiguously as just "Status" or "Fulfillment Status" — use "Order Status" for the `status` column specifically; `meta.fulfillment_status` already owns the "Fulfillment Status" name (it's customer-facing via `Api\OrderResource`) and must not be reused for something else in the admin panel.
- Mail Blade views (`resources/views/mail/*.blade.php`) have no CSS inliner — every base style must stay inline on the element. `@media` breakpoints are **additive only**: add classes alongside the existing inline styles (see the `.stack-col`/`.stack-gap`/`.full-col`/`.mail-px` pattern, `ARCHITECTURE.md`), never delete or replace an inline style to "clean up," since non-`@media`-aware clients (older Outlook) only ever see the inline styles.
- Raw SQL against `attribute_data` (Lunar's JSON attribute column) — e.g. the `breed`/`solution`/`badge`/`q` filters in `ProductController@index` — must cast with `CAST(attribute_data AS CHAR)`. `AS TEXT` is Postgres-only and silently 500s every request on this MySQL database; this exact mistake shipped and broke the `badge`/`q` filters for a while before being caught (2026-08-02).
- **New redirect/hosted-checkout payment gateway** (Airwallex/Payoneer/PingPong precedent, added 2026-08-07): implement `App\Payments\Contracts\PaymentGatewayInterface` + a matching `App\Services\XService` (config via `Cache::remember(300, fn () => Setting::get($key) ?: config(...))`, placeholder-mode fallback when unconfigured — same shape as `StripeCardGateway`/`PayPalGateway`). Webhook idempotency goes in the **shared** `payment_webhook_events` table (`gateway`+`event_id` unique) and state transitions go through the **shared** `OrderOperationsService::syncRedirectGatewayPayment()` — don't create a new per-gateway `XWebhookEvent` table/`syncXPayment()` method like Stripe/PayPal each have, unless the new gateway actually needs extra fields those two don't (Stripe's fraud/card-brand fields are the reason it has its own).
- **A Filament `Forms\Components\Section` that has `->headerActions([...])` must also have an explicit `->key('unique-string')`.** Without it, Filament throws a runtime 500 ("must have a [key()] set in order to use actions") the moment that section renders for a real authenticated request — `php -l`/static analysis won't catch this, and a plain `curl` check on an unauthenticated page (e.g. a redirect-to-login 200/302) won't either, since the crash only happens once Livewire actually mounts the component. This shipped as a real production 500 on `/admin/payment` (5 gateway tabs, each with a "Test X" button moved into its own `Section::headerActions()`) and was only caught by the user's screenshot, not by pre-deploy checks. **Always verify a Filament page/resource change with a real `Livewire::test(PageOrResourceClass::class)->assertSuccessful()`** (authenticated as a `super_admin` — see the next bullet) before considering it deployed, not just a syntax check or an unauthenticated `curl`.
- **Filament Shield policies gate Resources but not necessarily Pages, and only `super_admin` bypasses everything.** `AppServiceProvider`'s `Gate::before` returns `true` only for `hasRole('super_admin')`; a freshly-created `'admin'`-role test user gets 403'd on Shield-generated Resource policies (confirmed on `PostResource`/`BlogTagResource`/`PageResource` Livewire tests) even though the same role passed fine on a plain `Filament\Pages\Page` test elsewhere. Always `actingAs()` a `super_admin` user in Filament render tests, not `admin`, unless the test is specifically about permission boundaries.
- **Filament panel-wide CSS** (`AdminPanelProvider.php`'s `HEAD_END` render-hook `<style>` block): any selector meant for the actual left sidebar **must** be scoped with `nav.fi-sidebar`/`aside.fi-sidebar` (see the existing rules for the pattern). Filament reuses the exact same `.fi-sidebar-item-button`/`.fi-sidebar-item-label` classes for a resource's record sub-navigation panel (e.g. Product Edit's "Basic Information / Availability / Media / …" tabs) — an unscoped rule styling those classes for a dark sidebar (near-white hover text) silently makes that sub-nav's hover text unreadable on its light background. This exact bug shipped and was fixed 2026-08-07.
- **Feature tests seeding `Language`/`Currency`/`Role` rows must use `firstOrCreate()`, never `create()` (added 2026-08-13).** Two migrations (`2026_05_22_000001_ensure_lunar_default_records.php`, `2026_05_22_000003_ensure_lunar_roles_seeded.php`) already seed a default `en` Language, `USD` Currency, and `super_admin`/`customer` Roles before any test runs. A test's `setUp()`/fixture helper that unconditionally `create()`s one of those exact rows throws a unique-constraint/`RoleAlreadyExists` exception at `setUp()` time — which fails *every* test in the class with the same generic error, masking whatever the tests actually check. This caused ~21 silent pre-existing failures across `AdminAuthTest`/`CartApiTest` before being root-caused and fixed 2026-08-13 (see `ARCHITECTURE.md`). Every other test file already used `firstOrCreate()` for this — match that pattern for any new fixture that touches these tables.
- **A Filament widget referenced only via a Page's `getHeaderWidgets()` is not automatically registered with Livewire — it must also be added to the panel's `->livewireComponents([...])` array (or `discoverWidgets()` must be enabled).** Livewire's `ComponentRegistry` only learns about a widget class through explicit panel registration; a widget that's only ever instantiated by a Page's `getHeaderWidgets()` renders fine on the page's first server-rendered load (its HTML is baked into that response) but throws `ComponentNotFoundException` (a 500) on any subsequent AJAX round-trip Livewire itself has to dispatch against it (a poll, a filter change, etc.). This shipped for `AffiliateClicksOverview`/`TopClickedPostsWidget`/`ClicksByNetworkWidget` (fixed 2026-08-13 by adding all 3 to `AdminPanelProvider.php`'s existing `->livewireComponents([...])` array). A first-load screenshot or a plain page-load `curl` will not catch this — verify a new widget by triggering an actual AJAX interaction against it (a poll tick, a filter/action click) or by calling `ComponentRegistry::getName()`/`getClass()` directly for the widget class.
- **One design token, one purpose — never reuse a color token for both a hover-background and a text-only accessible color.** `secondary.dark`/`secondaryHover`/`text-secondary-dark` (`#c9713a`) was originally a hover-background-only token (lighter, meant to look like a subtle darken of the brand orange on `:hover`). A 2026-08-13 WCAG-AA contrast fix reused that same token for orange-as-text-on-white (which needs ~6.6:1 contrast, much darker than a pleasant hover background needs) — this shipped as a real, user-caught regression ("orange buttons look too dark on hover now"). Fixed by splitting into two dedicated tokens: `secondary.dark`/`secondaryHover` stays the original lighter `#c9713a` (hover-background only), and a new `rust` (`#8f4a1f`, 6.63:1 against white) is text-only, never a background. Renamed all `text-secondary-dark` usages to `text-rust` sitewide. **When adding a new accessible-contrast color, check whether the token you're about to reuse already has a different, incompatible visual role — add a new token instead of overloading an existing one**, and document each token's single intended purpose in a code comment next to its value (see `tailwind.config.ts`/`uiTheme.ts`/`tokens.css`).
- **`ink` (`#1a2128`, near-black, added 2026-08-13) is for text/icons placed on top of the brand orange (`secondary`) background** — white-on-orange fails WCAG AA (2.78:1), `ink` passes (5.63:1) without changing the orange itself. **`rust` (`#8f4a1f`, added 2026-08-13) is for orange-as-text on white/light backgrounds** (eyebrow labels, prices) — plain `text-secondary` fails AA as text (needs ~4.5:1, orange-on-white doesn't clear it). Don't use `ink`/`rust` for anything else, and don't introduce a third variant of "darker orange" without checking whether one of these two (or `secondary.dark`, hover-backgrounds only) already covers the case.
- **`{{business_phone}}` / `{{business_address}}` / `{{business_address_inline}}` are the only placeholder tokens `ContentController::renderPlaceholders()` substitutes into CMS page content (added 2026-08-13).** They resolve from `setting('business_phone')`/`setting('business_address')` — edit the Business Phone/Address fields in Filament, not the page's rich-text content directly, or the value drifts out of sync on the next admin edit to that field. `{{business_address}}` renders through `formatAddressMultiline()` (groups city+state/zip onto one line for a standard 4-part "Street, City, State Zip, Country" address, falls back to converting every comma to `<br>` for any other shape); `{{business_address_inline}}` is the raw un-formatted string. Don't hand-type the phone/address into a new legal/CMS page's content — use these tokens so an admin Settings edit propagates automatically.
- **A `Lunar\Models\Price` fixture must be created through the purchasable's own relation (`$variant->prices()->create([...])`), never with a hand-set `'priceable_type' => ProductVariant::class`.** Lunar registers a morph map (`ModelManifest::morphMap()`) that aliases model classes to short keys (e.g. `product_variant`, not the raw `Lunar\Models\ProductVariant` FQCN) — a `Price` row inserted with the literal class name as `priceable_type` is invisible to `$variant->prices` / `PricingManager::get()` (which filters by the resolved morph type), throwing `MissingCurrencyPriceException` the moment checkout/cart tries to price that variant, even though the row exists in the DB and looks correct on inspection. This exact bug shipped in `CartApiTest`'s `createVariant()` helper (fixed 2026-08-13) — `CheckoutApiTest`'s own `createPurchasableVariant()` already did this correctly via `$variant->getMorphClass()`; follow that helper as the reference, not the one that broke.
- **Never add `->name(...)` to a route in `routes/api.php` (added 2026-08-15).** `bootstrap/app.php`'s `withRouting(..., then: ...)` callback re-registers the entire file a second time under `/api/v1`, so any named route in it inevitably collides with itself. Uncached routing tolerates the duplicate silently, but `php artisan route:cache` throws "Another route has already been assigned name X" — which fails container boot and puts the backend into a crash-restart loop, since `route:cache` typically runs during the Docker image build/entrypoint. This shipped as a real production crash-loop (2026-08-15, root-caused via `docker ps` showing "Restarting" and reading `bootstrap/app.php`). If a feature seems to need Laravel's signed-URL mechanism (`URL::temporarySignedRoute()`/`hasValidSignature()`), both depend on route names — use a self-rolled `hash_hmac('sha256', "$payload|$expires", config('app.key'))` token instead (see `ContentController::hasValidPreviewToken()`, the Draft Preview feature's actual implementation) and validate with `hash_equals()` + a manual expiry check. Always run `php artisan route:cache` locally after touching this file, not just `php -l`, before considering a routes change deploy-safe.
- **A Filament `Select` field for a status/lifecycle column (e.g. Post's `status: draft|published`) does not auto-populate a paired timestamp column (`published_at`) just because the status value implies one.** They're independent form fields — a user can set Status to Published and save without ever touching Published At, leaving it `NULL`. If a public-facing query filters on that timestamp (`ContentController::posts()`'s `where('published_at', '<=', now())`, so future-dated posts stay hidden), a published record with a null timestamp is silently excluded from every list endpoint while still being directly reachable by slug (the single-post endpoint only checks `status`) — a confusing "it's published but nowhere on the site" bug that shipped for the first real post (2026-08-15). Fixed by auto-filling `published_at = now()` in both `CreatePost`/`EditPost`'s `mutateFormDataBeforeCreate`/`mutateFormDataBeforeSave` whenever `status === 'published'` and the field is empty. Any new status-driven timestamp (e.g. an `archived_at`) needs the same auto-fill, not just a bare form field.

**TypeScript/React (frontend)**
- `"use client"` is the literal first line of the file, no blank line before it, blank line after, then imports.
- Pages (`app/**/page.tsx`) are thin wrappers that render one component from `components/`. All logic lives in the component.
- No new state-management library, no axios/swr/react-query. Use `fetch()` against `getApiBaseUrl()` (`lib/api.ts`). This is deliberate — don't add a data-fetching library to "improve" it.
- Any component using `useSearchParams()` must wrap its default export in `<Suspense>` — the App Router build fails otherwise.
- ESLint flat config (`eslint-config-next`) — run `npm run lint`. No Prettier; ESLint is the only formatter config present, don't add one.
- **Read `frontend/AGENTS.md` before writing non-trivial Next.js/React code.** This Next.js/React version postdates most model training data; check `node_modules/next/dist/docs/` for APIs you're unsure about instead of assuming.
- Body/label text should use the design-token scale (`text-xs`/`text-sm`/etc., `tailwind.config.ts`) where possible, not arbitrary `text-[Npx]` values — a repo-wide sweep (2026-07-30) found ~365 hardcoded-px text sizes with no responsive breakpoint, several unreadably small on mobile. When a spot genuinely needs a value off the token scale, pair it with a `md:` breakpoint (e.g. `text-[13px] md:text-[16px]`) rather than one fixed size for every viewport — desktop-only elements (`hidden md:block` nav, etc.) don't need a mobile variant at all.
- Guest-owned data tied to a user (saved address, wishlist, …) is **localStorage-only for guests, server-only once logged in, with no merge-on-login** — established by checkout's guest "save address" and repeated for the wishlist (`ARCHITECTURE.md`). Don't build a guest→account sync/merge step unless explicitly asked; the existing precedent deliberately keeps guest data device-local and throwaway.
- The real product-listing API field for a sale/strikethrough price is **`comparePrice`** (`Api\ProductResource`, sourced from Lunar's `Price.compare_price`) — `oldPrice` only ever exists in mock data (`lib/shopData.ts`) and was never populated by the real API. This has already caused one shipped bug (`ProductCard.tsx` read `oldPrice` only, so the strikethrough price silently never rendered anywhere in production — fixed 2026-08-04). Any new component reading a product's old/compare price must read `comparePrice` (with `?? oldPrice` only as a defensive fallback for mock-data call sites, matching `ProductDetails.tsx`'s existing pattern), not `oldPrice` alone. Same failure class as the earlier `reviewCount`/`reviews` mismatch — when adding a field to `Api\ProductResource`, grep the frontend for every place a `Product` is rendered, not just one component.
- **Every public-content route needs its own `alternates: { canonical: '/path' }` in `metadata`/`generateMetadata` (added 2026-08-10).** `SITE_URL` (`lib/site.ts`) is `https://petposture.com` (non-www, canonical domain — `www.petposture.com` 301s to it via a Cloudflare Redirect Rule, see `README.md`/`ARCHITECTURE.md`). There is no site-wide default canonical set in `app/layout.tsx` — `metadataBase` alone does **not** add a canonical tag, only resolves relative URLs *given inside* one. A new page under `app/` that skips `alternates.canonical` silently ships with no canonical tag at all (this was the actual state of all 21 public routes until this date). For a dynamic route, build it from `params`, not a hardcoded string (e.g. `` alternates: { canonical: `/blog/${slug}` } ``).
- **Legal pages are CMS-driven, not hardcoded components (rebuilt 2026-08-09).** Privacy Policy, Terms and Conditions, Cookie Policy, Acceptable Use Policy, Affiliate Disclosure, Shipping Policy, and Return & Refund Policy now read from the backend `pages` table (`GET /api/pages/{slug}`) through one shared `components/LegalPageLayout.tsx`, which auto-derives the sticky table-of-contents by parsing `<h2>` tags out of the fetched content HTML (slugified into anchor ids) rather than a hardcoded `SECTIONS` array per page. **Don't add a new one-off `*Page.tsx` component for a new legal/info page** — add a `Page` row via Filament (Content Management → Pages) and a thin `app/<slug>/page.tsx` that calls `fetchCmsPage()` (`lib/pages.ts`) and renders `<LegalPageLayout page={...} />`, following the existing 7 as the template. **Every such route must export `const dynamic = 'force-dynamic'`** — without it, Next statically prerenders the page at Docker build time, and since the backend isn't reliably reachable during that isolated build stage, a failed fetch gets permanently baked in as a 404 (this exact bug shipped and was caught only by checking the build output's route-type column, `○` vs `ƒ`, before deploying — see `ARCHITECTURE.md`). No `@tailwindcss/typography` plugin exists in this repo — `LegalPageLayout`'s prose styling is hand-coded via arbitrary Tailwind variants (`[&_h2]:...`, `[&_ul]:list-disc`, etc.) on the content wrapper; don't rely on a bare `prose` class doing anything. `Page.is_core = true` pages (all 7 today) have their Delete action hidden/guarded in `PageResource` — don't add a way to delete a core legal page from the UI. Register any new legal page's URL in `Footer.tsx`'s `legalLinks`/`getLegalHref()` (and `bottomBarLegalLinks`, if it belongs in the bottom bar's 4-link set) same as before — that part didn't change. **Contact Us and Track Your Order are intentionally NOT part of this CMS** (they're functional tools — a real form, a live order-lookup — not flat content) and **FAQs is not either** (structured `{category, question, answer}[]` accordion data, not prose — would need a repeater-based editor, not a rich-text field, if ever migrated).
- **Business contact info (phone, office address) must be read from `useSettings().contact`, not hardcoded (added 2026-08-13, same pattern as `social`).** The backend already exposes `contact.phone`/`contact.address` on `GET /api/settings`, sourced from the admin's Business Phone/Business Address fields (Filament → SEO & Social) — but `ContactPage.tsx`, `Header.tsx`, and `TrackOrderPage.tsx` all had the real number/address typed as literal strings, so an admin edit never showed up anywhere on the storefront. Fixed by adding `contact` to `SettingsContext.tsx`'s `ShopSettings` shape and wiring all three consumers to it. Any new component that displays the business phone/address must read `useSettings().contact`, not a hardcoded string — grep the frontend for the current number/address before assuming there's only one place to fix, same lesson as the `comparePrice`/`reviewCount` field-drift bugs above.
- **A page that must never be edge-cached (checkout, cart, account, or anything reading per-request/per-user state) needs an explicit `export const dynamic = 'force-dynamic'`, even if nothing about it obviously looks server-rendered.** `/checkout` and `/checkout/success` are both fully `"use client"` pages with no server-side data fetch — but Next.js still statically prerenders a client page with no dynamic segment config, and ships a cacheable `Cache-Control: s-maxage=3600` header on that static shell. Cloudflare's zone-wide "Cache HTML pages" rule (any non-`/api/` path, `bypass_by_default` — i.e. caches only if the origin's own header allows it) then dutifully cached that stale shell for up to an hour after every frontend deploy, a bug that went unexplained from 2026-07-26 until root-caused 2026-08-13 (see `ARCHITECTURE.md`). **`dynamic` cannot be exported from a file with `"use client"` at the top** — if the page needs both, move the client content into `components/<Name>.tsx` unchanged and make `app/<route>/page.tsx` a thin server wrapper that only exports `dynamic = 'force-dynamic'` and renders `<Name />` (see `app/checkout/page.tsx`/`app/checkout/success/page.tsx` for the exact pattern). Verify via a production build — the route-type table must show `ƒ (Dynamic)`, not `○`/`●`, for any such route.

## Error handling

- **Controllers**: validate with `Validator::make(...)->validate()` or inline `ValidationException`; wrap risky calls in `try { ... } catch (ValidationException $e) { throw $e; } catch (\Throwable $e) { Log::error(...); return response()->json(['message' => ..., 'code' => ErrorCode::X->value], 4xx/5xx); }`. Let `ValidationException` bubble — don't catch-and-reformat it.
- **Services**: throw `ValidationException::withMessages(['field' => ['message']])` for business-rule failures. This is the only exception type application code should throw for expected failure cases.
- **Non-critical external calls** (AfterShip, IP intelligence, a confirmation email sent *after* the primary record already saved successfully — e.g. `NewsletterController::sendConfirmation()` — etc.): `catch (\Throwable $e) { Log::warning(...); }` — no rethrow, no user-facing error. These are side effects, not the main flow; the caller already got what they asked for. **Known unfixed instance**: `AuthController::register()`'s `Mail::send(new WelcomeEmail(...))` is unguarded — a mail failure there fails the whole registration response even though the account was already created (see `ARCHITECTURE.md`).
- **Frontend**: every `fetch()` call checks `res.ok`, reads `errorData.message` from the JSON body for the user-facing error, and never throws an unhandled promise rejection into the UI — always caught and surfaced as a state variable.
- Never swallow an exception silently (empty catch block). Log it, even for soft-fail paths.

## Docker / deploy

- Backend image: `dunglas/frankenphp:1.2-php8.3-alpine`, `composer install --no-dev --optimize-autoloader --no-scripts`, supervisord runs FrankenPHP + queue worker + scheduler (`schedule:work`) together. Migrations run automatically on container start — don't add a manual migrate step to the deploy script.
- Frontend image (`Dockerfile.prod`): single-stage `node:20-alpine`, `npm ci && npm run build`, runs custom `server.js` (not `next start`).
- `docker-compose.prod.yml`: all three services (`redis`, `backend`, `frontend`) use `network_mode: host`. Don't add a bridge network or a `ports:` section — that's not how this stack is wired.
- Deploy = SSH to VPS → `git pull` → `docker compose -f docker-compose.prod.yml build <service>` → `up -d --force-recreate <service>`. There is no CI pipeline; `build.js` (repo root, runs on `git push`) is a local push-time smoke build only — it does **not** run on the VPS and does **not** run tests/lint.
- **Local backend dev deps get wiped on every `git push`**: `build.js`'s push-hook smoke build runs `composer install --no-dev`, which strips Pint/PHPStan/Pail/PHPUnit/Faker from the local `backend/vendor/`. If `php artisan serve` (or anything needing those) errors with `Class "Laravel\Pail\PailServiceProvider" not found` right after a push, run `composer install` (no flag) again before debugging further — it's not a real regression.
- **Never leave a hotpatch (`docker cp` into a running container) undeployed.** It's for same-session testing only — the next real deploy (`git pull` + rebuild) silently overwrites it. Always follow up with a real commit + push + redeploy once a change is approved.
- After every deploy: run `npx gitnexus analyze` (per root `CLAUDE.md`) and run `php artisan optimize:clear` inside the backend container.
- After every **frontend** deploy: also manually purge Cloudflare (`docker exec petposture-backend php artisan tinker --execute='app(App\Services\CloudflareCacheService::class)->purgeAll();'`) and verify with a public `curl` — `/checkout` has been observed served stale from the edge otherwise (see `ARCHITECTURE.md` known-gap note). Don't assume the deploy took effect just because the container restarted cleanly.
- **Never probe the live public domain (`petposture.com`/`api.petposture.com`) with automated/scripted requests** (checking for exposed `.env`, looping to test rate limits, etc.) — a host-level `fail2ban` jail (`nginx-badbots`, see `ARCHITECTURE.md`) bans an IP from *every path, every site on the VPS* on a single matched scanner-pattern request, and that ban has already collaterally locked out a real customer sharing a CGNAT IP with the probing session. Probe `127.0.0.1:8001` (backend) / `127.0.0.1:3001` (frontend) directly on the VPS instead — bypasses Cloudflare and this nginx layer entirely, same result, zero blast radius. If you must hit the public domain to test edge-layer behavior specifically, keep it to one or two requests, not a loop.
- **A "Googlebot"/"bingbot"/etc. User-Agent in `nginx`/fail2ban logs is not proof of the real crawler** — scanners routinely spoof well-known good-bot UA strings to blend in or evade naive allowlists. Verify via the IP's actual owner (`curl "http://ip-api.com/json/<ip>?fields=isp,org,as,reverse"` — no `whois` binary needed) before treating a ban as a false positive or before ever whitelisting a UA string outright.

## Forbidden / avoid

- `laravel/cashier` — Stripe is integrated by hand (`StripePaymentIntentService` + custom gateway). Don't introduce Cashier.
- A third-party PayPal SDK package (`srmklive/paypal`, `paypal/paypal-checkout-sdk`, etc.) — PayPal is integrated by hand (`PayPalService` + `Payments/Gateways/PayPalGateway.php`), mirroring the Stripe pattern. Don't introduce a PayPal SDK package.
- A third-party SDK for Airwallex, Payoneer, or PingPong — same as Stripe/PayPal, integrated by hand via raw `Http::` calls in `AirwallexService`/`PayoneerService`/`PingPongService` + their matching `Payments/Gateways/*Gateway.php`. Don't introduce an official/community SDK package for any of the three.
- Any frontend state library (Redux, Zustand, Jotai, etc.) or data-fetching library (axios, SWR, React Query) — not present, not wanted. Plain `fetch()`.
- Prettier — no config exists; don't add one, ESLint is the single source of formatting truth on the frontend.
- Markdown-based Mailables (`Content(markdown: ...)`) for anything customer-facing — all customer emails are custom `Content(view: ...)` Blade for design control. New customer emails follow that pattern, not Lunar's/Laravel's default markdown mail.
- Manual order `status` writes outside `OrderOperationsService` — breaks the state machine, the customer emails, and the outbound webhook dispatch that are all wired to go through it.
- `--no-verify` / `--no-gpg-sign` on git operations, and destructive git commands (`reset --hard`, `push --force`) without explicit user instruction.
- One-off debug/audit scripts (`scratch_*.php`, `tools/debug_*.php`, `out_*.txt` command-output dumps, etc.) committed into the repo — 51 of these had accumulated in `backend/` before a 2026-08-04 cleanup removed them. Keep throwaway scripts in the scratchpad/temp directory, never `git add` them; `backend/.gitignore` now has patterns (`scratch_*.php`, `out_*.txt`, `/tmp/`, `/tools/`) to catch the common cases.
